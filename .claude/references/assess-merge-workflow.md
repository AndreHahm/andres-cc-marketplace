# /assess-md-merge

## Workflow

### Phase 1 — Identify Inputs

#### Large-File Two-Pass Strategy

Before reading a file in full, check its line count. If a file exceeds **500 lines**:

1. **First pass — structure scan:** Read only headings (`##` / `#` lines) and the frontmatter block. This reveals the section tree, document type, and whether the file is a documentation dump, a hybrid command/doc file, or a lean skill. Identify which sections are novel relative to the other source.
2. **Second pass — targeted read:** Read only the sections identified as novel or high-priority in pass 1. Skip sections whose headings clearly duplicate content already present in the other source.

Record in the assessment which sections were skipped in pass 2 and why. Do not skip sections that contain Must Preserve candidates.

For files under 500 lines, read in full (no two-pass needed).

---

For each file, extract:

```text
filename
document_type
frontmatter
title
main purpose
target audience
runtime identity
invocation rules
output contract
reference links
external file references
tool permissions
model/runtime settings
severity schema
examples
constraints
safety rules
```

#### Format-Construct Detection

After extracting fields, scan each file for non-standard Markdown constructs that require conversion before or during the merge:

| Construct | Pattern | Default Conversion |
|---|---|---|
| MDX `<Steps>` | `<Steps>...</Steps>` | Numbered list |
| MDX `<Tabs>` / `<Tab>` | `<Tabs>...</Tabs>` | `###` subsections |
| MDX `<Note>` / `<Warning>` / `<Tip>` | `<Note>...</Note>` etc. | Blockquote with bold label (`> **Note:** ...`) |
| Fenced directive | `:::note ... :::` | Blockquote |
| Command-style routing | directive blocks, `@command`, `!execute` | Flag for strip |
| Auto-generated doc blocks | `<!-- generated -->`, `<AutoGenerated>` | Flag for removal |

Record any detected constructs as `format_constructs_detected: [list]` per file. This list is consumed by Phase 13 to populate format-conversion directives in the Merge Instruction Block.

Classify each file as:

```text
skill
subagent
slash-command
reference
checklist
project-rule
prompt
unknown
```

### Phase 1.5 — Frontmatter Schema Validation

For each file that has a YAML frontmatter block, validate all fields against the platform schema for the detected target type.

**Known valid fields by target type:**

| Target Type | Valid Fields |
|---|---|
| `skill` | `name`, `description`, `model`, `color`, `tools`, `permissionMode`, `hooks` |
| `subagent` | `name`, `description`, `model`, `color`, `tools`, `permissionMode`, `hooks` |
| `slash-command` | `description`, `allowed-tools` |
| `reference` | none enforced |
| `checklist` | none enforced |
| `project-rule` | `globs`, `alwaysApply` |

For each frontmatter field found:

- **Valid field** (in the list for this target type): mark as `valid — may preserve`.
- **Non-standard field** (not in the list): mark as `non-standard — platform will reject — cannot preserve`.
  - Do not include non-standard fields in `Must preserve` in the Merge Instruction Block.
  - Do not raise a `human_decision_required` trigger for non-standard fields — the resolution is unambiguous: drop the field and log it (per Phase 4.5 Obvious-Resolution Pre-Filter).

Record findings in the assessment under a **Frontmatter Schema** subsection:

```text
name: skill-development — valid
description: ... — valid
version: 0.1.0 — non-standard for skill — platform will reject — cannot preserve
allowed-tools: [...] — non-standard for skill — platform will reject — cannot preserve
```

This check runs before Phase 4 (Hard Conflicts) so that non-standard fields are pre-resolved and excluded from the conflict analysis.

### Phase 2 — Determine Document Relationship

Classify the relationship between the files:

```text
same-entity
same-entity-style-drift
same-topic-reference-expansion
specialized-variant
base-plus-overlay
variant-set
related-but-separate
conflicting-documents
unrelated-documents
```

Use these criteria:

| Relationship | Meaning |
|---|---|
| `same-entity` | Same name, same purpose, compatible structure |
| `same-entity-style-drift` | Same runtime identity, different wording or organization |
| `same-topic-reference-expansion` | Same topic, different reference depth or lifecycle phase |
| `specialized-variant` | One file is a narrower version of another |
| `base-plus-overlay` | One file is a general base, another adds conditional behavior |
| `variant-set` | Multiple useful variants should remain separate |
| `related-but-separate` | Same domain, different purpose |
| `conflicting-documents` | Similar identity but incompatible behavior |
| `unrelated-documents` | Not suitable for merge |

### Phase 3 — Detect Merge Drivers

Identify why a merge might be useful.

Possible drivers:

```text
duplicate content
style drift
fragmented references
frontmatter drift
outdated version
missing sections
different output formats
same topic across repositories
reference expansion
skill consolidation
slash-command normalization
subagent standardization
```

If no strong merge driver exists, mark the planned merge as low-value.

### Phase 4 — Detect Hard Conflicts

Hard conflicts increase merge risk.

Check for:

```text
different names
different runtime identities
different target document types
incompatible output contracts
JSON-only vs prose output
different tool permissions
different model/runtime settings
conflicting safety rules
conflicting severity schemas
different invocation semantics
different reference path conventions
different licensing
different authorship/version lineage
active testing or security authorization requirements
```

Classify conflicts:

| Conflict Level | Meaning |
|---|---|
| `none` | No relevant conflict |
| `soft` | Can be resolved through composition or documentation |
| `medium` | Requires explicit merge strategy |
| `hard` | Merge may damage behavior or intent |
| `blocking` | Do not merge without human decision |

### Phase 4.5 — Identify Human Decision Required Triggers

Some conflicts must force an explicit human decision before any merge can proceed.

#### Obvious-Resolution Pre-Filter

Before raising `human_decision_required`, check whether the conflict has an unambiguous resolution. If yes, record the resolution under a **Pre-Resolved Conflicts** subsection in the assessment and do NOT raise a human decision gate.

A conflict has an unambiguous resolution when:

- **Name conflict where output path is predetermined**: the target output path, output directory, or existing canonical directory name dictates which name wins. Record the winning name and the reason (e.g., "`output` is `plugins/.../hook-development/` → `name=hook-development` wins").
- **Invalid frontmatter field for target type**: the field is not part of the target type's schema (e.g., `argument-hint` or `allowed-tools` in a skill file that has no tool invocations). Resolution: drop the field and log it.
- **Format construct in one source with no equivalent in the other**: MDX components, command-style routing blocks, or scraped documentation sections that clearly do not belong in the target file type. Resolution: strip and convert per Phase 1 Format-Construct Detection directives. Flag for validation but not for human decision.
- **Version field where one value is strictly higher**: the higher version wins. Record both values and the decision.

Only conflicts where **both resolutions are plausibly correct** and the choice has **behavioral consequences** are escalated to `human_decision_required: true`.

Require explicit human decision when any of these are present:

- output contracts are incompatible
- tool permissions differ and include `Write`, `Bash`, deploy, delete, network, or external side-effect actions
- active testing, exploitation, reconnaissance, or destructive validation is involved
- licensing differs or is unclear
- authorship or version lineage is unclear
- two files have different runtime names or command identities
- one file requires JSON-only output and another requires prose output
- safety gates exist in only one source
- one source contains approval, deployment, deletion, payment, or credential-handling behavior
- a merge would change who or what invokes the resulting skill, subagent, command, or workflow

When one of these triggers appears, set:

```text
human_decision_required: true
```

Then document:

```text
decision_required_for: <specific topic>
recommended_default: <safe default>
reason: <why the human decision matters>
```

Default to the safer or more conservative option in the recommendation.

### Phase 5 — Assess Information Loss Risk

Estimate whether a merge could lose context.

Check whether the merge might:

- remove useful variants
- weaken mandatory constraints
- hide runtime differences
- collapse separate output modes incorrectly
- normalize references incorrectly
- discard examples
- lose safety gates
- lose severity semantics
- overwrite metadata
- make the result less executable
- make the result harder to maintain

Assign:

```text
information_loss_risk: low | medium | high | critical
```

### Phase 5.5 — Define Context Loss Budget

Define what may be lost or compressed during the merge and what must never be lost.

Use this structure:

```markdown
## Context Loss Budget

Allowed loss:
- duplicate wording
- redundant examples
- repeated section headings
- equivalent descriptions
- repeated checklist items with the same operational meaning

Not allowed loss:
- runtime metadata
- output contracts
- safety gates
- external links
- reference paths
- severity semantics
- invocation rules
- tool permissions and permission rationale
- licensing, authorship, or version metadata
- examples that demonstrate different behavior
- constraints written as MUST, MUST NOT, Always, Never, or equivalent
```

Use the `Not allowed loss` list as merge acceptance criteria.

If a source contains stricter rules than another source, the stricter rule is normally not allowed to be lost unless the final recommendation is `do-not-merge` or a human explicitly chooses otherwise.

### Phase 6 — Assess Maintainability Impact

Evaluate whether the merged result would be easier or harder to maintain.

Consider:

- one file vs multiple files
- future update burden
- reference stability
- runtime clarity
- command discoverability
- duplication reduction
- risk of oversized documents
- need for modular references
- likely future variants

Assign:

```text
maintainability_impact: improves | neutral | worsens | uncertain
```

### Phase 7 — Assess Executability Impact

For skills, subagents, and slash-commands, check whether the merged result would remain executable.

Verify:

- required tools are allowed
- commands in the body match allowed tools
- output format remains clear
- invocation rules remain unambiguous
- runtime metadata remains valid
- permission model does not accidentally escalate
- least-privilege principle is preserved

Assign:

```text
executability_risk: low | medium | high | blocking
```

### Phase 8 — Assess Safety Impact

For security, automation, agents, or workflows with external effects, check whether the merge affects safety.

Look for:

- active testing
- exploit validation
- production changes
- write access
- destructive commands
- credential handling
- deployment steps
- data deletion
- external API calls
- user approval gates
- human escalation gates

Assign:

```text
safety_risk: low | medium | high | blocking
```

If safety gates are present in one source but missing in another, recommend preserving or strengthening the stricter gate.

### Phase 9 — Score Merge Suitability

Score each dimension from 0 to 5. For each dimension, record the score assigned and the one-sentence rationale so the total is auditable.

Fill this table in the assessment output:

| Dimension | Max | Score | Rationale |
|---|---|---|---|
| Identity alignment | 5 | | (same name / related names / unrelated) |
| Purpose alignment | 5 | | (same goal / overlapping / different goals) |
| Output compatibility | 5 | | (fully compatible / composable / incompatible) |
| Metadata compatibility | 5 | | (compatible / resolvable drift / hard conflict) |
| Reference compatibility | 5 | | (same paths / resolvable drift / conflicting) |
| Safety compatibility | 5 | | (compatible / one source stricter / unsafe conflict) |
| Deduplication value | 5 | | (high overlap / moderate / minimal) |
| Maintainability gain | 5 | | (clearly improves / neutral / worsens) |
| **Total** | **40** | | |

Anchor scores (use 0, 1–2, 3, 4–5 as bands — not just 0 and 5):

| Score | Meaning |
|---|---|
| 5 | Fully aligned / maximum value |
| 4 | Mostly aligned, minor gap |
| 3 | Partial alignment, some drift |
| 1–2 | Significant misalignment |
| 0 | Incompatible / no value |

Interpretation:

| Score | Recommendation |
|---:|---|
| 34–40 | Merge recommended |
| 26–33 | Merge conditionally recommended |
| 18–25 | Merge only with explicit strategy |
| 10–17 | Merge not recommended |
| 0–9 | Do not merge |

Hard or blocking conflicts may override the score.

### Phase 9.5 — Determine Merge Readiness Level

Convert the recommendation, score, hard conflicts, and risk assessments into a direct readiness level.

Use one of:

```text
READY
READY WITH CONDITIONS
NEEDS HUMAN DECISION
NOT READY
BLOCKED
```

Use these rules:

| Readiness Level | Meaning | Typical Trigger |
|---|---|---|
| `READY` | Merge can proceed with normal validation | high score, no meaningful conflicts |
| `READY WITH CONDITIONS` | Merge is useful but must follow explicit constraints | medium/high score with resolvable drift |
| `NEEDS HUMAN DECISION` | Merge may be useful, but at least one decision affects behavior, safety, licensing, or runtime identity | hard conflict, permission escalation, output contract conflict |
| `NOT READY` | Merge is currently a poor choice; use an alternative structure | low score, unclear relationship, maintainability worsens |
| `BLOCKED` | Merge must not proceed until a blocking issue is resolved | unsafe conflict, incompatible safety rules, unrelated documents |

Hard or blocking conflicts may lower readiness even when the numeric score is high.

Examples:

```text
Merge Suitability Score: 31 / 40
Merge Readiness: READY WITH CONDITIONS
```

```text
Merge Suitability Score: 24 / 40
Merge Readiness: NEEDS HUMAN DECISION
```

### Phase 10 — Choose Recommended Strategy

Recommend one of:

```text
canonical-single-file
base-plus-overlay
variant-preserving
reference-pack
index-plus-linked-files
diff-report-only
do-not-merge
```

Use these rules:

| Situation | Recommended Strategy |
|---|---|
| Same entity, compatible output | `canonical-single-file` |
| Same entity, style drift only | `canonical-single-file` |
| Same topic reference expansion | `canonical-single-file` or `reference-pack` |
| Base document plus specialized behavior | `base-plus-overlay` |
| Multiple valid variants | `variant-preserving` |
| Large related docs with distinct purposes | `index-plus-linked-files` |
| Unclear relationship | `diff-report-only` |
| Hard conflicts or unrelated files | `do-not-merge` |

### Phase 11 — Suggest Better Alternatives

If merge is not the best choice, suggest a better structure.

Possible alternatives:

#### Base + Overlay

Use when one document is general and another is conditional or specialized.

```text
base.md
overlay-specialized.md
```

#### Variant Set

Use when multiple variants should remain independently usable.

```text
skill.md
skill-strict.md
skill-fast.md
skill-security-focused.md
```

#### Index + Linked Files

Use when documents are related but too large or distinct to merge.

```text
README.md
references/security-checklist.md
references/security-hardening.md
references/security-output-format.md
```

#### Reference Pack

Use when several reference files belong together but should remain modular.

```text
security-review/
  checklist.md
  owasp-map.md
  llm-security.md
  examples.md
```

#### Diff Report Only

Use when the purpose is understanding differences, not producing a new canonical file.

```text
merge-assessment.md
```

#### No Merge

Use when files have incompatible runtime behavior, conflicting safety models, or unrelated purposes.

### Phase 12 — Produce Final Assessment

The final output must include:

```markdown
# Markdown Merge Assessment

## Recommendation

MERGE RECOMMENDED / MERGE CONDITIONALLY RECOMMENDED / MERGE NOT RECOMMENDED / DO NOT MERGE

## Short Rationale

Brief explanation in 3–6 sentences.

## Relationship Classification

Detected relationship and why.

## Merge Suitability Score

Include the completed dimension table from Phase 9 (Dimension / Max / Score / Rationale) followed by the total score and interpretation band. Do not replace the table with a bare score — the per-dimension rationale makes the score auditable and reproducible.

## Key Alignment Points

What supports a merge.

## Key Risks

What makes the merge risky.

## Hard Conflicts

List hard or blocking conflicts.

## Recommended Strategy

Recommended structure.

## Better Alternative

Only if merge is not the best option.

## Conditions Before Merge

Only if merge is conditionally recommended or recommended with non-trivial constraints.

## Merge Instruction Block

A copy-ready instruction block for `/merge-md-context`.

## Merge Readiness

READY / READY WITH CONDITIONS / NEEDS HUMAN DECISION / NOT READY / BLOCKED

## Decision Options

A table of user options and when to choose each option.

## Context Loss Budget

Allowed loss and not-allowed loss for the planned merge.

## Suggested Next Step

Clear next action for the user.

## Recommended Invocation

A copy-ready `/merge-md-context` invocation when merge is recommended or conditionally recommended.
```

### Phase 13 — Produce Merge Instruction Block

If the recommendation is `MERGE RECOMMENDED` or `MERGE CONDITIONALLY RECOMMENDED`, produce a copy-ready block that can be pasted directly into `/merge-md-context`.

If the recommendation is `MERGE NOT RECOMMENDED` or `DO NOT MERGE`, either omit the block or produce an alternative-structure block instead.

The block must convert assessment findings into operational merge constraints.

Use this structure:

```markdown
## Merge Instruction Block

Copy this block into `/merge-md-context` if you decide to proceed.

```text
target_type=<detected-target-type>
merge_strategy=<recommended-strategy>
preferred_style=operational
strictness=conservative
output_mode=merged-file-with-report

Files:
- <file-a>
- <file-b>

Must preserve:
- <unique content that must not be lost>
- <metadata, references, output formats, constraints, examples>

Must resolve:
- <conflicts or drift points that require explicit decisions>
- <severity mappings, output-mode decisions, reference path drift>

Must not:
- <behaviors the merge must avoid>
- <constraints that must not be weakened>
- <unsafe tool or permission escalation>

Validation checklist:
- [ ] All Must preserve items are present in the merged file.
- [ ] All Must resolve items are explicitly resolved or documented.
- [ ] No Must not item was violated.
- [ ] Merge Report documents conflicts and decisions.
```
```

#### Format-Conversion Directives

When `format_constructs_detected` is non-empty for any source file (from Phase 1), add a `Format conversion` section inside the Merge Instruction Block. Directives must be specific and actionable — not "handle MDX" but "convert `<Steps>` to numbered list."

```text
Format conversion:
- <source> contains MDX <Steps>: convert to numbered list.
- <source> contains MDX <Tabs>: convert to ### subsections, one per tab.
- <source> contains MDX <Note>/<Warning>/<Tip>: convert to blockquote with bold label (e.g., > **Note:** ...).
- <source> contains command-style routing blocks: strip entirely — no standard Markdown equivalent.
- <source> contains auto-generated doc blocks: remove; flag any unique content extracted from them.
```

If a construct has no safe standard Markdown equivalent, state so explicitly and add a `Must not` item to prevent it from appearing verbatim in the merged file.

#### Must Preserve

Use `Must preserve` for information that must survive the merge unchanged or semantically intact.

Examples:

```text
Must preserve:
- Risk-gated scope assessment.
- JSON-only output mode.
- External references and relative paths.
- Authorization gate before active testing.
- Confidence threshold ≥ 80.
- Positive feedback requirement.
```

#### Must Resolve

Use `Must resolve` for known conflicts or drift that the merge must handle deliberately.

Examples:

```text
Must resolve:
- Severity model drift: Critical/Major/Minor vs Critical/High/Medium/Low.
- Reference path drift: `reference/` vs `references/`.
- Tool permissions: keep least-privilege unless preserved behavior requires more.
- Scope fallback: do not hardcode only `HEAD~1`.
```

#### Must Not

Use `Must not` for behaviors that would make the merge unsafe, ambiguous, or lower quality.

Examples:

```text
Must not:
- Drop safety gates.
- Merge incompatible output contracts without explicit output modes.
- Add `Write` permission unless the final document explicitly performs write actions.
- Suppress security escalation for speed.
- Remove external links or reference files.
```

#### Validation Checklist

Use the validation checklist as the acceptance criteria for the merge output.

### Phase 14 — Produce Recommended Invocation

When the assessment recommends or conditionally recommends a merge, produce a complete copy-ready invocation for `/merge-md-context`.

The invocation must include:

- command name
- detected target type
- recommended strategy
- preferred style
- strictness
- output mode
- file list
- mandatory merge instructions from the Merge Instruction Block

Use this structure:

```markdown
## Recommended Invocation

```text
/merge-md-context
target_type=<detected-target-type>
merge_strategy=<recommended-strategy>
preferred_style=operational
strictness=conservative
output_mode=merged-file-with-report

Files:
- <file-a>
- <file-b>

Mandatory merge instructions:

Must preserve:
- ...

Must resolve:
- ...

Must not:
- ...

Validation checklist:
- [ ] ...
```
```

If the recommendation is `MERGE NOT RECOMMENDED` or `DO NOT MERGE`, replace this with a copy-ready alternative-structure plan.

### Phase 15 — Produce Decision Options Matrix

End the assessment with a concise decision matrix.

Use this structure:

```markdown
## Decision Options

| Option | When to choose | Result |
|---|---|---|
| Proceed with merge | You accept the conditions and readiness is READY or READY WITH CONDITIONS | Run `/merge-md-context` |
| Proceed after decision | A human decision is required, but you choose an explicit resolution | Run `/merge-md-context` with added decision notes |
| Keep separate | You want to preserve variants or runtime roles | Use `variant-set` or `base-plus-overlay` |
| Create index | Files are related but too large or distinct | Use `index-plus-linked-files` |
| Create reference pack | Related references should stay modular | Use `reference-pack` |
| Stop | Conflicts are blocking or value is low | Do not merge |
```

The matrix must reflect the actual assessment. Remove irrelevant options when appropriate.


The checklist should be specific enough that the merged result can be reviewed against it without re-reading the full assessment.

### Phase 16 — Write Assessment to File

Determine the run directory:

1. If `run_dir` was explicitly provided, use it.
2. Otherwise compute: `.claude/output/<artifact-slug>-<YYYY-MM-DD>/`
   - `artifact_slug`: lowercase kebab-case of the target merged filename. If not yet known, derive from the first source file by stripping trailing version suffixes (`-1`, `-2`, `-3`, `(1)`, `(2)`) and lowercasing.
   - `YYYY-MM-DD`: today's date.
3. If the directory does not exist, create it.
4. If a directory for the same artifact slug already exists:
   - If `manifest.md` shows this is the current session: reuse the directory.
   - If `assessment.md` already exists and is from a prior session: do not overwrite. Append `-2`, `-3`, etc.
   - If the existing directory is incomplete (`⏳ pending` steps in `manifest.md`): offer to resume from the next incomplete step instead of restarting.

Write `assessment.md` to the run directory containing the full output from Phases 1–15.

Append a pre-filled suggested invocation for the next step at the end of `assessment.md`:

````markdown
## Suggested Next Step

```text
/merge-md-context
target_type=<detected-target-type>
merge_strategy=<recommended-strategy>
preferred_style=operational
strictness=conservative
output_mode=merged-file-with-report
run_dir=<run_dir>

Files:
- <source-a>
- <source-b>

assessment_block: <run_dir>/assessment.md
```
````

**Manifest:** If `skip_manifest=true`, skip the manifest write — the calling pipeline writes the manifest itself at completion. Otherwise write or create `manifest.md` in the run directory:

```markdown
## Pipeline Run: <artifact-slug>

| Step | Status | File | Date |
|---|---|---|---|
| `/assess-md-merge` | ✅ complete | `assessment.md` | YYYY-MM-DD |
| `/merge-md-context` | ⏳ pending | — | — |
| `/review-merged-md` | ⏳ pending | — | — |
| `/document-merged-md-artifact` | ⏳ pending | — | — |

## Source Files

- `<source-a>`
- `<source-b>`

## Run Directory

`.claude/output/<artifact-slug>-<YYYY-MM-DD>/`
```

Report the run directory path in the chat response.
