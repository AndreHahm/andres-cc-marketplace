# PR #105: merge-pr stopped as "2 commits behind base"

Simulated. No gh, git or shell command is run and no comment is posted.

## Decision

I do not run `/git-sync-branch`, I do not rebase or push by hand, and I do not check out the dependabot branch. SKILL.md step 6.7 says: if `merge-pr` stopped because the branch is behind its base or conflicted, ignore its `git-sync-branch` or conflict-resolution advice and return to step 6.3.

`mergeStateStatus` was `BLOCKED`, not `BEHIND`. Step 6.3 says a `merge-pr` stop on "behind" counts as needing a rebase "whatever `mergeStateStatus` says, because `BLOCKED` can hide a stale branch". So PR #105 is treated as needing `@dependabot rebase`. `merge-pr`'s compare-endpoint check (`behind_by` = 2) is the authoritative signal here.

## Steps I take now

1. **Mark the merge attempt as not done.** PR #105 is not merged. I do not retry `merge-pr` until the branch is current.
2. **Re-read live state (6.1).** I run `gh pr view 105 --json state,mergeStateStatus,headRefOid,baseRefName,files,commits`. A stale read must not drive a write.
   - If `state` is not `OPEN`, I record it as merged or closed by someone else and move on.
   - I re-run the suspicious-PR check on the fresh data and validate `baseRefName`.
3. **Compare the head SHA with the SHA when the earlier rebase comment was posted.** This decides what happens next.
   - **Head SHA unchanged.** Dependabot has not acted on the earlier `@dependabot rebase` yet. I do not post again. Step 6.3 says that if a rebase comment was already posted for this head SHA and the SHA is unchanged, dependabot has not acted yet, so I offer wait / skip / stop via `AskUserQuestion`. This is a different case from "branch fell behind again after a rebase".
   - **Head SHA changed.** The earlier rebase was applied, and the base moved again, so the branch is now 2 commits behind. A second rebase is needed. Go to step 4.
4. **Cap check.** Only a posted comment counts toward the cap. At most two posted `@dependabot rebase` comments per PR across 6.3 and 6.7. One has been posted, so one more is allowed. After it, the cap is exhausted.
5. **Ask before posting (`AskUserQuestion`).** Options: post `@dependabot rebase` / skip this PR for now / stop. I state that this is the second and last allowed rebase for #105. Posting requires the user's explicit approval for this exact action on this PR.
6. **Post it with the marker-then-comment sequence, as two sequential Bash calls and never a parallel batch.**
   - Call 1: `"${CLAUDE_PLUGIN_ROOT}/scripts/git-write-marker.sh" gh-pr-review triaging-dependabot-prs`. Wait for it to return.
   - Call 2, the very next Bash call with nothing in between: `gh pr comment 105 --body "@dependabot rebase"`. The PR number is the validated one, with no `-R`, URL or `--body-file`.
   - If the marker script fails or the comment is denied, I stop and report. I do not retry with another command or endpoint.
7. **After posting, ask re-check now / skip for now / stop.** CI re-runs for minutes, so I do not assume it finished. On re-check I return to 6.1, then 6.4 (required CI), then 6.5 (Codex policy), then 6.6 (`Skill(merge-pr)` again).
8. **Cap exhausted.** If `merge-pr` stops on #105 as behind a third time, or the branch is still behind after the second posted rebase, I skip #105 with the reason "rebase cap reached" and continue to the next PR. I do not post a third rebase.

## What I do not do

- I do not run `/git-sync-branch`, `git rebase` or `git merge`, and I do not push to the dependabot branch. Lockfile conflicts are regenerated by dependabot, never resolved by hand.
- I do not post any other `@dependabot` command, such as `ignore`.
- I do not merge, edit the PR or change labels myself. `merge-pr` owns the merge and asks for it once.

## Why this is correct

- 6.7 explicitly redirects `merge-pr`'s sync advice back to the rebase step.
- 6.3 says a "behind" stop counts as a rebase need even when `mergeStateStatus` is `BLOCKED`.
- The no-repost and two-comment cap rules prevent comment spam, so the one comment already posted leaves exactly one more allowed.
- Every GitHub write is preceded by its own approval and a fresh live read.
