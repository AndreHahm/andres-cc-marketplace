WHICH WORKFLOW IS RISKY, AND WHY
---------------------------------
fixtures/risky.yml is the risky one -- critical severity, score 9. Contents:

  name: Risky CI
  on: [push, pull_request_target]

  jobs:
    deploy:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@main
        - uses: actions/setup-node@v4
        - run: echo "no permissions, no timeout, floating refs"

Four independent hardening gaps, all flagged by the script:

1. No workflow-level or job-level permissions: block -- the deploy job runs with the repository's
   default (often overly broad, e.g. write on contents) GITHUB_TOKEN permissions.
2. No timeout-minutes on the deploy job -- a hung/runaway job has no automatic cutoff.
3. Two floating action refs:
   - actions/checkout@main -- a mutable branch ref (branch-like), not pinned; whatever is on main
     at run time gets executed.
   - actions/setup-node@v4 -- a mutable major-version tag (major-tag); v4 can be repointed to a new
     commit at any time by the action's maintainer.
4. Triggered on pull_request_target (alongside push) -- this event runs with access to repository
   secrets and a write-scoped token even for PRs from forks, which is the highest-risk trigger
   combined with unpinned actions and no permissions floor. This is exactly the pattern the audit is
   designed to catch before it reaches production CI.

fixtures/clean.yml is not risky -- ok severity, score 0. It declares workflow-level
permissions: { contents: read }, its one job has timeout-minutes: 10, its only uses: ref is pinned
to a full commit SHA (actions/checkout@de0fac2e... with a "# v6.0.2" comment), and it only triggers
on push to main (no pull_request_target).
