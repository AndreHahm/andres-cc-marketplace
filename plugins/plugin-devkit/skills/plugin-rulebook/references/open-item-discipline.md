# Open-Item Discipline

Checks shared by `plugin-lifecycle-upstream`, `plugin-lifecycle-downstream`, and `plugin-lifecycle-maintenance` — each skill's own SKILL.md/workflow states *when* in its own procedure these run; this file is the single source of truth for *how* they run, so the disclosure wording and bar for "resolved" don't drift out of sync across three separate skills. See this file's own section headers below for the current full list — don't restate the count or names elsewhere, since a restated enumeration is exactly what goes stale the next time a section is added here (as happened once already). One section (Downstream's Proactive Offer) is specific to `plugin-lifecycle-downstream` alone; the rest apply to all three.

## Phase-Completion Check

**Purpose:** catch a phase (or workflow step) getting marked complete despite owning unresolved sub-work of its own — most commonly a sub-agent dispatch cancelled mid-run by a session limit, but also a batched dispatch where only some batches returned, or a check that was supposed to run against every item in a set but silently stopped partway through.

**Procedure:**
1. Before presenting a phase's gate (or, for a workflow step with no formal gate, before moving on to the next step), review what that phase actually dispatched in this run and confirm each dispatch either completed normally or was explicitly recorded as skipped-with-reason.
2. If any dispatch was cancelled, errored, or left incomplete — a session-limit interruption, a tool crash with no retry, a batch that never returned — do not present the phase as cleanly complete. State plainly what didn't finish, and what (if anything) still needs a follow-up run.
3. This is a disclosure requirement, not a blocking one: an incomplete sub-dispatch does not have to be resolved before the phase can advance — the run can proceed with the gap named as an open item, the same non-blocking-disclosure pattern `plugin-lifecycle-upstream`'s own "unplanned overhead" note at its Test gate already uses for a comparable class of mid-run friction.
4. **A large SKILL.md (or other component-file) rewrite gets an immediate targeted re-review, not just a wait for the next full grading round.** "Large" means a substantive rewrite of a section's actual behavior/contract, not a wording tweak — a real instance: a rewrite that added "hand off to X" language introduced a defect (X turned out to have `disable-model-invocation: true`, making the hand-off impossible) that its own same-round reviewer dispatch didn't catch; a full fresh multi-agent re-grade a round later was what finally surfaced it. A cheap, targeted check run immediately after the rewrite — e.g. grep every skill named in "hand off to X"/"delegates to X" language for that skill's own `disable-model-invocation` or equivalent invocability field — catches this class of defect without waiting for the next expensive full re-grade.

## Pre-Commit Disclosure

**Purpose:** catch a run that reaches a commit step while findings surfaced earlier in that same run — an unaddressed Self-Review finding, a Test failure recorded as skipped, a Phase-Completion gap from an earlier phase, a mirror-sync gap (below) — were never explicitly resolved or explicitly declined by the user.

**Procedure:**
1. Immediately before any Commit step in any of the three lifecycle skills, collect every open item surfaced during the current run: Phase-Completion gaps (above), Self-Review findings the user didn't approve for action, Test/smoke-check failures or skips, items an `enhancement-suggestor` plan classified as non-Quick-Win (Strategic Investment / Reconsider), Quick Wins the user declined, mirror-sync gaps (below), and any other item explicitly flagged but left unresolved.
2. **Mirror sync check, part of this same step, not a separate gate to invoke:** for every plugin-devkit component file this run actually edited, `Glob` for every *tracked mirror copy* of that same path — `.claude/skills/<name>/...` and `plugins/plugin-devkit/skills/<name>/...` are always a mirror pair, and must end byte-identical (diff them; a mismatch is a real gap to close before staging, not just a disclosure item). `.agents/skills/<name>/...`, when it exists for that component, is **not automatically a third mirror copy** — some `.agents/` components are genuine Codex-CLI-adapted variants (different paths like `.codex/output/...`, different prose referring to Codex sessions/AGENTS.md) that must *not* be made identical to the `.claude/` copy; others are stale near-mirrors of the same Claude-Code-facing content that *should* be kept in sync but were never touched by an intentional adaptation. Tell the two apart by reading the `.agents/` copy, not by assuming: if its content is substantively about Codex CLI (different tool ecosystem, different config paths), it's an adapted variant — note the divergence as intentional and move on. If it reads as the same Claude-Code-facing skill with only incidental differences (a stray find-replace artifact, a missing recent addition), it's a stale mirror — sync it like the other two. `.claude/worktrees/` and `.codex/worktrees/` are gitignored and never count as a tracked copy to sync.
3. If the collected list (including any mirror-sync gap) is non-empty, state it plainly to the user as part of presenting the commit (file list + message) — before the commit itself runs, not folded silently into the commit message and not omitted on the assumption the user already saw it earlier in the run. For a deferred-by-classification item specifically, state its classification label and one-clause reason, not just its name — pull this from `enhancement-suggestor`'s own `## Deferred Items` list rather than re-deriving it. If the commit message itself carries a `Deferred:` line, that line must also state the reason, not only the item name.
4. An empty list is a normal, common outcome — state "no open items" rather than omitting the line entirely, so its absence isn't mistaken for the check not having run at all.

**Why mirror sync lives inside this check, not as its own gate:** a separate top-level "Mirror Sync" section previously existed here but named no invocation point in any of the three lifecycle skills, so it could never actually fire. Pre-Commit Disclosure is already the one checkpoint all three skills invoke immediately before every commit — folding mirror sync in as one more thing this same check collects reuses a real invocation point instead of adding a fifth one that would need its own wiring into three separate SKILL.md files.

**When a fix is fragmented across multiple agents** (one component or file set per agent), state the mirror-sync requirement explicitly in each agent's own dispatch instructions too, rather than relying solely on this closing check to catch every agent's own omissions — the closing check is a backstop, not a substitute for each agent doing its own sync as it goes. A tracked-but-stale mirror copy fails R19/R20 (`plugin-rulebook`) on a later, unrelated check if it slips through both — catching the drift here, at the point it was introduced, is cheaper than waiting for that later check to surface it.

## Downstream's Proactive Offer

**Scope:** `plugin-lifecycle-downstream` only. The other two lifecycle skills stop at the Pre-Commit Disclosure above; this is an addition specific to downstream's own end-of-run behavior, not a shared procedure.

**Procedure:** at the end of a downstream run, if any open item remains — from Pre-Commit Disclosure, or surfaced afterward (e.g. a declined Deep Test, an unresolved Self-Review finding from Phase 5) — do not just list the items and stop. Ask via `AskUserQuestion`: "N open item(s) remain from this run — implement them now?", with per-item or consolidated options to proceed. This mirrors the same "offer the next step, don't just report and end" pattern downstream's own Suggested Next Step already uses for Phase 3/Deep Test, applied here specifically to items that would otherwise be left to a future, unscheduled run — or forgotten.

## Why This Is Shared, Not Restated Per Skill

Three lifecycle skills, three different phase structures — but "did this phase's own work actually finish" and "does the user know what's still open before we commit" are the same two questions regardless of which pipeline is asking them. Keeping the wording and the disclosure bar in one file means a future change to any check (e.g. tightening what counts as "explicitly resolved") lands once, not three times across three separately-maintained SKILL.md files — the same reasoning `branch-and-pr-preflight.md` already established for the Open-PR and Branch-scope checks.
