# Smoke Tests

Persistent, mostly dependency-free Node scripts verifying specific behavior fixes in codex-kit. Each file targets one component and exits `0` on all-pass, `1` on any failure — no test framework required. The one exception is `codex-exec-live-roundtrip.mjs`, which requires a real, authenticated `codex` CLI and consumes API quota when it runs live (see its own row below and "When to re-run").

Run from `plugins/codex-kit/`:

```bash
node scripts/smoke-tests/commands-arg-handling.mjs
node scripts/smoke-tests/codex-review-bridge-trust-boundary.mjs
node scripts/smoke-tests/codex-review-bridge-semantic-validation.mjs
node scripts/smoke-tests/codex-review-bridge-total-inspection-failure.mjs
node scripts/smoke-tests/codex-exec-schema-validation.mjs
```

Or all at once:

```bash
for f in scripts/smoke-tests/*.mjs; do node "$f" || echo "FAILED: $f"; done
```

## What each one covers

| File | Component | What it verifies |
|---|---|---|
| `commands-arg-handling.mjs` | `commands/status.md`, `result.md`, `transfer.md`, `cancel.md`, `review.md`, `adversarial-review.md` | The underlying `codex-companion.mjs` subcommands still work when invoked as separate, individually-quoted arguments (the pattern these commands now instruct the model to use, instead of interpolating a raw `$ARGUMENTS` blob). The `review`/`adversarial-review` cases use a deliberately-invalid `--scope` value so the check exercises real argument parsing while failing fast, before ever reaching Codex — these two never spawn a real review. |
| `stop-review-gate-hook.mjs` | `hooks/hooks.json`'s Stop hook (`scripts/stop-review-gate-hook.mjs`) | The hook's exported `parseStopReviewOutput`/`buildStopReviewPrompt` functions directly: ALLOW/BLOCK/malformed-output decision logic, and that the previous turn's assistant message lands inside its own delimited `<claude_response_evidence>` block (not `<task>`) with explicit trust-boundary framing text present. |
| `codex-review-bridge-trust-boundary.mjs` | `skills/codex-review-bridge/scripts/bridge-invoke.mjs` | The containment check rejects an `--instruction-file` that resolves inside `--target-paths` (the self-referential-reviewer-instructions case), and does not false-positive on a legitimately trusted, outside-scope instruction file. Also: `CODEX_KIT_REVIEW_MODEL` and `CODEX_KIT_REVIEW_TIMEOUT_MS` env-var validation both fail fast on a malformed value before any Codex call. |
| `codex-review-bridge-semantic-validation.mjs` | `skills/codex-review-bridge/scripts/bridge-invoke.mjs` | `semanticallyValidate`'s optional `components[]` finding field: a valid entry passes, omitting `components[]` entirely stays backward compatible, and the pre-fix workaround (a multi-path string crammed into `location` alone) still never becomes a validated finding — proving the fix adds a field rather than loosening the existing `location` check. Also (issues #236/#111): an out-of-scope or nonexistent `location`/`components[]` citation is dropped per-finding/per-citation with an `inspection_limits` note, not rejected as a whole envelope, while a `dispatch.id`/`dispatch.reviewer` mismatch or duplicate finding id still reject the entire envelope. Post-cross-model-review fix (2 rounds): a dropped-citation note is a fully static string with zero interpolated values — round 1 removed the raw `location`/`component` text, round 2 removed `finding.id` too (also unconstrained, model-controlled) — and a crafted `location`, `component`, or `id` containing process-start-failure phrasing (e.g. `"CreateProcessAsUserW"`) is confirmed to NOT trip `isTotalInspectionFailure` once dropped. Post-GitHub-review fixes (Devin + Codex on this PR): a finding's `components` stays `null` when it started `null`, distinguishable from a multi-file finding whose components all got dropped (which becomes `[]`); and the envelope fails closed (rejects the whole envelope) when every originally-returned finding gets dropped, rather than returning `ok: true` with an empty `findings` array indistinguishable from a genuine clean pass — confirmed a genuinely-empty-to-begin-with findings list and a mixed dropped/surviving case both still validate correctly. |
| `codex-review-bridge-total-inspection-failure.mjs` | `skills/codex-review-bridge/scripts/bridge-invoke.mjs` | `isTotalInspectionFailure` (issue #78): a schema-valid, zero-finding envelope whose `inspection_limits` reports the sandbox couldn't start a process (`"Windows error 1920"` / `CreateProcessAsUserW`-shaped text) is detected, so `main()` can reclassify it into the resolver-visible `isolation_profile_unavailable` typed failure instead of it looking like a genuine clean pass. An ordinary partial-limitation note, a genuine clean pass with empty `inspection_limits`, and a non-empty `findings` array (proving real findings suppress the reclassification) are all confirmed NOT to trigger it; malformed/missing input never throws. Post-security-review fixes: (M2) a partial read/access note with no process-start signature no longer over-matches; (M1, source-level) `main()`'s `semanticallyValidate` dispatch-identity check is confirmed to run BEFORE `isTotalInspectionFailure`, with a controlled negative proving the assertion would catch a reverted ordering. ## When to re-run

- After any further edit to the SKILL.md/command files listed above.
- As part of `plugin-lifecycle-upstream`'s Phase 5 (Test) bounded smoke check for this plugin, or `plugin-lifecycle-downstream`'s Deep Test step for deterministic-script coverage.
- These are static/mechanical checks (bash template correctness, RPC auth logic, XML well-formedness) — they do **not** call the real Codex CLI or consume API quota, except where noted: `broker-rpc-auth.mjs` spawns a real broker process, which in turn spawns a real `codex app-server` process, but never sends it a review/task request; `codex-exec-live-roundtrip.mjs` does send one real, minimal `codex exec` request and requires a live, authenticated `codex` CLI (it SKIPs cleanly, rather than failing, when one isn't available).
